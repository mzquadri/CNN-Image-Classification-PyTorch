# Review

Read of this repository at `5986991`, 24 October 2026. It records what the code does,
what was run to check it, what was wrong, and what was deliberately left alone.

Guidance applied, named where it was used: Google's Engineering Practices for the code
read, GitHub's "Security hardening for GitHub Actions" for the workflow, the Twelve-Factor
App for the dependency and configuration pins, Diataxis and GitHub's README guidance for
the documentation, Conventional Commits is **not** used here because this repository's
history uses sentence-style subjects and consistency with it is worth more, PEP 8 with
ruff for the Python, and gitleaks for the secret scan.

## What it does

It trains a small convolutional network on a 15,000-image subset of CIFAR-10 and then
measures what that result is worth by putting three other models either side of it: a
constant predictor, logistic regression on raw pixels, and a ResNet-18 starting from
ImageNet weights, all on the same images and the same twelve epochs.

The repository separates two things that are easy to conflate. `src/train_fast.py` is the
script that produced the originally published run, and its outputs are kept in
`results/test_results.json`, `results/training_history.json` and `results/figures/`.
`src/benchmark.py` is the later, fully seeded harness that reproduced that run and added
the three comparison arms, and its output is `results/benchmark.json`. `src/train.py` is a
full-dataset, fifty-epoch script that has never been run.

## What works, and what was run to establish it

Everything below was executed locally on this machine before anything was changed.

| Check | Command | Result |
|---|---|---|
| Lint | `python -m ruff check .` | 1 finding, discussed below |
| README against results | `python scripts/check_repository.py` | **38 of 38** recorded numbers found, 20 required files present, `src/` compiles |
| Parameter count | same script | the built `nn.Module` has **815,018** parameters, matching the results file |
| Tests | `python -m unittest discover -s tests` | **25 tests, 22 passed, 3 skipped** |
| Figures | `python scripts/figures/generate_figures.py` | 3 of 4 regenerated **byte-identically**, 1 skipped |
| Secret scan | `gitleaks detect --source .` | **no leaks**, 10 commits, 939.83 KB scanned |

Three results are worth more than the ticks suggest.

**The recorded metrics recompute from the recorded predictions.**
`tests/test_metrics.py::RecordedMetricsFollowFromRecordedPredictions` reloads the stored
per-image predictions and recomputes every accuracy, macro F1, per-class score and
confusion cell in `results/benchmark.json`, requiring exact agreement. That is the
property that makes a committed results file evidence rather than an assertion, and it is
the reason continuous integration can verify a GPU run it never performs.

**The figures regenerated byte-identically on a different toolchain.** `requirements.txt`
pins `torch==2.11.0`, `numpy==2.4.3` and `scikit-learn==1.8.0`; this machine has torch
2.7.1, numpy 2.3.3 and scikit-learn 1.7.2. matplotlib matched at 3.10.8. Three of the four
figures came out identical under `git diff --exit-code` regardless. The fourth,
`04_failure_examples.png`, is the only one that needs the image data and was skipped.

**The three skipped tests and the skipped figure are the same cause**, not a gap: CIFAR-10
is a 170 MB download that `.gitignore` excludes, so anything needing the raw images skips
when it is absent. That is the correct behaviour and `5986991` is the commit that
introduced it.

## What was wrong

### 1. The architecture diagram presented one run's numbers as the result, and nothing checked them

`docs/diagrams/architecture.svg` carries a results strip reading **"Test accuracy
64.26%"**, "Best: automobile 82.0%" and "Hardest: cat 33.5%". Those are the **original**
run's figures, from `results/test_results.json`. The README now opens with the
reproduction, **63.82%**, and only reaches 64.26% inside a table whose left column is
headed "Original run".

Neither number is wrong. The defect is that the diagram does not say which run it is
describing, so a reader who sees 63.82% in the first paragraph and 64.26% in the diagram
below it has nothing to tell them these are two runs rather than one contradiction.

`scripts/check_repository.py` asserts the SVG **exists** and nothing about what it says.
This is the same shape as the defect recorded in `PROGRESS.md` for
`MLOps-End-to-End-Pipeline`: one number with two sources, one of them unchecked, which
drifts and then ships. Here it has not drifted yet, which is the moment to guard it.

The same strip also reads **"Full-data 50-epoch script included"**. That is literally
true, `src/train.py` defaults to `max_epochs: int = 50` on the full dataset, but it sits
among three measured accuracies, which reads as a result. The README's Limitations section
exists partly to retract the unmeasured 85% that script was once said to produce.

**Fixed** by labelling the strip as the original run, replacing the script badge with the
reproduced figure beside it, and adding both numbers and the per-class extremes to
`check_repository.py` so the SVG is now checked against `results/benchmark.json` and
`results/test_results.json` rather than merely required to exist.

### 2. `src/train_fast.py` says it uses the full dataset, and does not

Line 4 of its docstring: *"Uses full CIFAR-10 dataset but trains for fewer epochs."*
Line 84 of the same file: `subset_size = 15000`.

This matters more than a stale comment usually would. That script produced the headline
result the whole repository is built around, the README is explicit that the run used
15,000 of the 50,000 available training images, and the docstring is the first thing a
reader opening the file sees. It contradicts the README at the exact point where the
README is being careful.

**Fixed.** The docstring now says what the code does and points at the script that does
use the full dataset.

### 3. The lint result depended on which ruff you had, and the real Python floor was undeclared

`pyproject.toml` set no `target-version`, and there is no `[project]` table, so no
`requires-python` either. `ruff check --show-settings` confirms
`linter.unresolved_target_version = none`: ruff was falling back to its own built-in
default, which differs between releases.

The consequence is measurable. Continuous integration pins `ruff==0.16.1` and is green.
Current ruff, 0.17.0, reports `UP017` on `src/benchmark.py:344`, because that rule only
fires for Python 3.11 and above and the default target moved up between the two releases.
So a contributor running current ruff saw a failure CI did not, with no declared setting to
explain the difference.

The floor the code actually needs is **Python 3.12**, which was also undeclared. Checking
each target in turn, `--target-version py311` reports
`scripts/check_repository.py:217` as a syntax error: it uses a backslash escape inside an
f-string, which is PEP 701 and 3.12 only. CI happens to run 3.13, so this never surfaced.
A reader on 3.11 would have hit a syntax error with nothing in the repository telling them
3.11 was not supported.

**Fixed** by declaring `requires-python = ">=3.12"` and `target-version = "py312"`, and by
applying the `UP017` fix so the tree is clean under both ruff versions. The lint result no
longer depends on which ruff is installed.

### 4. The workflow was unhardened and two actions were on deprecated Node 20

Against GitHub's "Security hardening for GitHub Actions":

| Gap | Was | Now |
|---|---|---|
| Token scope | no `permissions` block, so the job took the repository default | `permissions: contents: read` at workflow level |
| Runaway cap | no `timeout-minutes`, so the default was **six hours** | `timeout-minutes: 15`, against an observed run well under it |
| `actions/checkout` | `@v4`, Node 20, deprecated | `@v7` |
| `actions/setup-python` | `@v5`, Node 20, deprecated | `@v7` |
| Dependency caching | none, so torch was downloaded on every run | `cache: pip` keyed on `requirements.txt` |

The major versions were read from the GitHub API rather than guessed. The
`MLOps-End-to-End-Pipeline` pass in `PROGRESS.md` records assuming two of four actions were
current and being wrong, so they were checked here.

### 5. The README overstated what continuous integration does, by one figure

It said CI "regenerates the figures". CI has no CIFAR-10, so
`04_failure_examples.png` is **always** skipped there: CI regenerates three of the four and
cannot check the fourth. **Fixed** to say so, because the whole argument of this repository
is that the committed artefacts are checked, and a reader is entitled to know which one is
not.

### 6. One label in the diagram fails WCAG AA, and there was no Mermaid diagram

Every text colour in `architecture.svg` was measured against **the fill it is actually
drawn on** rather than against the page, because most of the labels sit inside tinted
boxes. Seventeen of the eighteen pass WCAG AA. One does not:

| Label | Colour on fill | Ratio | Needed |
|---|---|---|---|
| "10 classes" | `#3b82f6` on `#eff6ff` | **3.38:1** | 4.5:1 |
| its three siblings | `#6d28d9` on `#faf5ff` | 6.62:1 | 4.5:1 |

At 10 px it is not large text under WCAG, so the 4.5:1 floor applies and 3.38 fails it. The
three equivalent labels in the convolutional boxes all pass comfortably, so this was an
inconsistency as well as a failure. **Fixed** to `#2563eb`, which measures **4.75:1** on
the same fill, is already in the diagram as that box's stroke colour, and keeps the
relationship the other boxes have of the shape label sitting lighter than the body text.

The next thinnest margins are the subtitle at `#64748b` on white, **4.76:1**, and the
accuracy badge at `#15803d` on `#f0fdf4`, **4.79:1**. Both pass and both were left.

The repository also had no Mermaid diagram, only the hand-written SVG and an ASCII block.
Two were added so GitHub renders them inline without an image: the architecture, built from
the real layer shapes, and the evidence path, which is the more useful of the two because
it shows where a GPU is needed and where it is not.

The SVG declares an opaque white background, so it stays legible in dark mode rather than
inverting, but it does not blend. A dark-themed variant is **not** in this change and is
listed under Next steps.

## What the README and the website claim, checked

**The README is the most thoroughly checked prose in this repository.** All 38 numbers it
quotes are re-derived from `results/benchmark.json` by `scripts/check_repository.py`, each
matched with its surrounding words so a value that moved sentence does not satisfy a check
by accident. No unverifiable claim was found in it. It also retracts, in writing, an
earlier claim of roughly 85% from fifty epochs on the full dataset, and says it was never
measured. That retraction is the correct handling and it is kept.

**The website's claims are true, and incomplete.** `ZQ/src/content/cifar-world.ts`,
`cifar-chapter.ts`, `portfolio.ts`, `ecosystem.ts` and `case-stories.ts` publish the
original run: 64.26%, the 33.5 to 82.0 per-class range, and a confusion matrix transcribed
from `results/figures/02_confusion_matrix.png`. Every one of those values was checked
against the files it cites and matches. The site also already says, in three separate
places, that this is a bounded educational baseline and not a competitive result, so it
never carried the "competitive without pretrained models" framing that this repository's
own README now reports as not surviving.

What the site does not have is the September work: the reproduction, the three comparison
arms, macro F1, and the duplicate audit. Its case study is titled "A Reproducible Baseline"
and its strongest limitation is that the aggregate hides a 48.5-point spread, which is
exactly the gap the new benchmark closed. Bringing it across is step 7 of this pass and is
tracked in `PROGRESS.md`, not here.

## Deliberately not changed

- **`src/train.py` has never been run, and it stays.** Fifty epochs on the full dataset
  needs a GPU session nobody has committed to, and deleting a script because its result was
  retracted would remove the thing a reader needs in order to run it themselves. It is
  described as unrun in the README and now in the diagram too.
- **`ruff format` is not enforced**, and running it would reformat source that is otherwise
  clean. That belongs in its own change with the CI step that would keep it true, which is
  the same call recorded for `insureassist-rag-mlops`.
- **The workflow pins actions by major tag, not commit SHA.** GitHub's hardening guidance
  prefers a SHA; consuming GitHub's own first-party actions by major tag is the documented
  alternative and is what the rest of this portfolio does, so it was left consistent.
- **`on: push` carries no branch filter**, so a pull request from a branch in this
  repository triggers two runs. It is wasteful rather than wrong, and narrowing it would
  silently stop checking pushes to branches nobody opened a PR for.
